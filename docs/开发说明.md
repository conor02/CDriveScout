# 开发说明

面向想改代码、加规则或自己打包的人。用户向的说明在 [用户手册](用户手册.md)。

---

## 一、技术栈

| 项 | 选择 | 原因 |
|---|---|---|
| 运行时 | Electron 45 | 需要真正的桌面窗口 + 直接的文件系统 API；纯浏览器做不到，纯脚本又不满足「能点击」 |
| 界面 | 原生 HTML/CSS/JS，无框架 | 界面只有一屏，引入 React/Vue 只会增加打包体积和心智负担 |
| 扫描 | Node `worker_threads` | 遍历几十万文件是 CPU 密集任务，放主线程会卡界面 |
| 打包 | `@electron/packager` | 比 electron-builder 轻，产物就是一个文件夹，符合「绿色软件」定位 |
| 第三方依赖 | **0 个运行时依赖** | 除 Electron 本体外不引用任何 npm 包，供应链面最小 |

> 为什么不用 C#/WinForms：编译产物只有几百 KB，本来是最优解，但当时的构建机安全策略禁止调用 `csc.exe`。
> Electron 的代价是 357 MB 的运行时，换来的是零编译依赖和跨机器可重现。

## 二、目录结构

```
CDriveScout/
├── main.js                 # 主进程：窗口、IPC、两条操作链路
├── preload.js              # 上下文隔离桥，只暴露白名单 API
├── rules.ini               # 分类规则（外置，运行时可改）

│   ├── rules.js            # 规则解析 + 分类判定（纯函数，易测）
│   ├── scanner.js          # 目录遍历（同步递归，跑在 worker 里）
│   ├── scan-worker.js      # 扫描线程入口：批次回传 + 进度节流
│   ├── ops.js              # 操作计划：路径映射、冲突避让、保护校验、空间检查
│   ├── ops-worker.js       # 迁移线程：流式复制 + 校验 + 时间戳
│   └── report.js           # CSV / HTML 报告生成

│   ├── index.html          # 单页结构
│   ├── style.css           # 全部样式
│   └── renderer.js         # 状态管理、虚拟滚动、对话框、导出
├── scripts/build.js        # 打包脚本（staging → packager → 补 rules.ini）
├── test/                   # 4 组单测 + 2 个端到端 + 截图脚本
└── docs/                   # 手册与截图
```

## 三、进程与线程模型

```
┌─────────────────────────┐
│ 主进程 main.js           │  窗口生命周期、IPC 路由、回收站调用、迁移编排
└───────┬─────────┬───────┘
        │ IPC     │ worker_threads
┌───────▼──────┐  ┌▼──────────────────────┐
│ 渲染进程      │  │ scan-worker  (扫描)    │
│ renderer.js  │  │ ops-worker   (复制校验) │
└──────────────┘  └───────────────────────┘
```

**为什么把扫描和复制都丢进 worker**：

- 扫描：42 万次 `lstat` 在主线程会让窗口假死，右键菜单都点不动
- 复制：大文件是长时间 IO，且需要能被中途取消（`parentPort.on('message')` + 分块检查）

**为什么扫描结果要分批回传**：一次 `postMessage` 传 40 万条会序列化几百 MB，峰值内存直接上 GB。
现在是攒满 2000 条发一批，渲染层增量累加，内存和首屏速度都可控。

## 四、数据流转

### 扫描

```
渲染层 startScan({root,minSize,skipSystemScan})
  → 主进程 new Worker(scan-worker)
    → scanner.scan() 递归遍历，命中 minSize 的条目进 buffer
      → 每 2000 条 postMessage({type:'batch',items})
      → 每 350ms postMessage({type:'progress'})
  → 渲染层收到 batch 就累加 + 重算分类计数（400ms 节流渲染）
  → 收到 done 收尾
```

停止扫描用的是「协作式中断」：主进程置 `token.cancel`，worker 在遍历循环里检查；
超时未停则 `terminate()`，已回传的批次仍然有效。

### 操作（回收站 / 迁移）

```
渲染层 collectSelection() → 主进程 op:plan
  → src/ops.js 生成计划：逐项校验（存在？受保护？超批量？）+ 路径映射 + 冲突避让
  → 返回 {ok, items, count, total, warnings}
  → 渲染层展示预览（第 1 步确认）→ 最终确认（第 2 步）
  → 主进程 op:run
      trash:   逐个 shell.trashItem（20s 超时/项）
      migrate: new Worker(ops-worker) 流式复制 → 校验 → 回传结果
               → 主进程把「校验通过」的原件 shell.trashItem
```

**关键设计：`ops-worker` 里没有任何删除源文件的代码。**
源文件的回收由主进程在拿到 `ok:true` 的结果后执行。这样即使复制线程被强杀，也不会出现「原件没了、副本也没写全」。

## 五、安全约束（改代码时必须守住）

| # | 约束 | 位置 |
|---|---|---|
| 1 | 扫描阶段零写操作 | `src/scanner.js` |
| 2 | 用户文件只走 `shell.trashItem` | `main.js` 的 `runTrash` / `runMigrate` |
| 3 | 目标同名文件一律放弃，绝不覆盖 | `src/ops.js` `uniquePath` + `ops-worker` 的 `wx` 标志 |
| 4 | 失败清理只处理「本次新写且大小不对」的副本 | `main.js` 与 `ops-worker.js` 的兜底段 |
| 5 | 受保护目录双重拦截（界面 + 主进程） | `src/ops.js` `checkItem` |
| 6 | 不跟随符号链接 / junction | `src/scanner.js` |
| 7 | 单次批量上限 800 | `src/ops.js` `MAX_BATCH` |

改动涉及以上任何一条，请同步更新单测并说明理由。

## 六、踩过的坑

这些都是真实发生过的，写下来避免重犯。

### 6.1 `--ignore` 在 Windows 下不生效，把历史产物打进了 asar

`electron-packager --ignore="^/dist"` 在 Windows 路径下匹配不上，结果旧的 `dist/`（377 MB）被整个塞进 `app.asar`。
第一次打包没出问题，只是因为当时 `dist/` 还空着 —— 属于运气。

**做法**：`scripts/build.js` 先建一个只含运行文件的 staging 目录，再对 staging 打包。不依赖 ignore 规则。
现在 `app.asar` 是 113 KB / 16 个文件。

### 6.2 worker 发完 `done` 不退出

`ops-worker.js` 结束后没有 `parentPort.close()`，它注册的 `on('message')` 让事件循环一直活着，
线程常驻不退 —— 每迁移一次泄漏一个线程。

**修法**：发完 `done` 后调 `parentPort.close()`。这个 bug 在单测里表现为「进程挂住不退出」，很容易发现。

### 6.3 目标已存在同名文件时，失败清理会删掉用户已有文件

早期版本在失败分支里无条件 `unlink(dst)`。如果 `dst` 是用户原本就有的文件（只是因为同名被跳过），
这一步会把用户文件删掉。

**修法**：清理前加两个条件 —— 文件必须是本次操作开始后写入的（`mtime >= opStart - 2000`）
且大小与源文件不符。同时写入用 `wx` 标志，目标存在直接失败，从根上不覆盖。

### 6.4 Electron 的环境变量污染

某些环境会注入 `ELECTRON_RUN_AS_NODE=1`，导致 Electron 退化成一个纯 Node 进程，启动即报 `app is not defined`；
`NODE_OPTIONS` 注入也会影响打包后的 exe。

**排查**：`env | grep -i "electron\|node_"`。启动时 `env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS`。

### 6.5 大文件被占用导致删不掉

删除/移动被进程占用的文件时，`rename` 会返回 `EBUSY`，父目录 `EPERM`。
用 Sysinternals `handle64.exe -a <文件名>` 或 Restart Manager 查持有者，别靠「大小/权限/配额」猜。

### 6.6 `ftruncate` 不是稀疏文件

想在测试里造一个「逻辑 3 GB、实占 0」的文件，`fs.ftruncateSync` 会真实分配簇（实测 3 GB 全分配）。
真要稀疏得先 `fsutil sparse setflag`。

## 七、构建

```bash
npm install
npm run build:exe        # → release/CDriveScout-win32-x64/
```

`scripts/build.js` 做四件事：

1. 把 `main.js preload.js package.json rules.ini LICENSE src/ renderer/` 复制到 `.build-staging/`
2. 调用 `@electron/packager` 对 staging 打包（`--platform=win32 --arch=x64`）
3. 把 `rules.ini` 补到产物根目录
4. 打印产物路径与体积

想换 Electron 版本：改 `package.json` 的 `devDependencies.electron`，脚本会自动读取实际安装的版本号。

国内下载 Electron 慢，可以先设镜像：

```bash
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
```

## 九、加一条规则 / 加一个功能

**加规则** → 只改 `rules.ini`，加完点「重新加载规则」即可，无需改代码。
规则顺序敏感，特例写前面。改完跑 `node test/test-rules.js` 确认没有误伤。

**加一个分类** → 需要改四处：`src/rules.js` 的 `CATEGORY` 常量、`renderer.js` 的 `CATS` / `CAT_CLASS` / `CAT_RANK`、
`style.css` 的 `.tag.xxx` 配色。分类是写死在代码里的五档，不建议扩。

**加一个操作类型** → 在 `src/ops.js` 加 `planXxx`，`main.js` 加 IPC 分支，`renderer.js` 加按钮与确认流程。
所有操作都必须复用现有的「预览 → 二次确认 → 执行 → 结果」四段式。

## 十、性能备忘

| 场景 | 数据 | 耗时 |
|---|---|---|
| 整盘扫描（42 万文件 / 80 GB，冷缓存） | C: 300 GB NVMe | 10.8 s |
| 同盘热缓存 | 同上 | ~6 s |
| 15,000 个文件的小目录 | 演示目录 | 0.1 s |
| 迁移 1.2 GB 单文件（含 SHA-256） | 机械/SSD 混合 | ~2 s |
| 表格渲染 10 万行 | 虚拟滚动 | 无明显卡顿（只渲染可视区 ± 12 行） |

扫描是单线程的，瓶颈在 `lstat` 系统调用。要再快只能直读 NTFS MFT（需要原生模块 + 管理员权限），
这是路线图里的事，不是当前瓶颈。
